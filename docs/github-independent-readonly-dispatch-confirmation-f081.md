# F-081 — independent read-only confirmation of GitHub sandbox dispatch evidence

## Scope

F-081 strengthens the manual authorization *review* protocol between
F-080's immutable dispatch intent and a future independently implemented
transport. It records a **second independent person's acknowledgement**
against one exact SHA-sealed F-080 handoff and its live F-078/F-055/F-052
lineage. **It does not grant write permission.**

There are still no GitHub mutations or subprocess-based remote push,
no refspecs, credentials, token minting, worker dequeue, claim, send
command, automatic retry, migration-complete indicator, or executable
authorization generated by this feature.

## API

Superadmin-only routes beneath
`/api/incremental-preparations/{preparationId}/operation-plans/{planId}/github-app-scopes/{scopeId}/remote-sandbox-review-sessions/{sessionId}/dispatch-intents/{intentId}`:

- `POST /confirmations`: no body. The JWT actor must differ from the
  recorded F-080 requester, F-078 session observer and all distinct
  F-052/F-050/F-055/F-047 operator actors.
- `GET /confirmations/{confirmationId}`: exact scoped, hash-verified
  historical inspection. A UUID outside its stored preparation, plan,
  scope, intent and session cannot be retrieved.

Like F-080, the routes are disabled by default, restricted to an
explicit numeric test-repository allowlist, and rate-limited
independently (eight requests per minute). With the feature disabled,
even a superadmin receives `SandboxDispatchConfirmationDisabled` and
there are no provider HTTP calls.

## Strict database invariant

`github_remote_sandbox_dispatch_confirmations` is initialized
**after F-080** and stores a unique confirmation per F-080 intent,
F-078 session and F-055 hazard. Its single `Confirmed` audit event
is a distinct append-only row.

Every confirmation is permanently
`ConfirmedWriteDisabled`; its `can_dispatch`,
`transport_invoked`, `may_automatically_retry` and
`migration_complete` flags are false. PostgreSQL CHECK constraints
enforce these values, two BEFORE UPDATE/DELETE triggers reject
tampering, and the canonical SHA-256 binds the exact intent SHA,
session SHA, source packet/candidate hashes, live ref digest,
numeric repository ID, both human identities and a DB-clock
expiry that cannot exceed any underlying authority deadline.

The write transaction acquires repository advisory locks 732911 then
733050, uses the PostgreSQL clock, validates F-080 (including audit)
and F-078 (including audit), and rechecks the current F-055 hazard,
F-052 grant, F-050 fence, F-047 attempt and F-045 lease. A
possible-send hazard marker, expired evidence or changed authority
prevents recording or replay. Six concurrent connections using the
same confirmer return the identical row, SHA and single audit; a
different confirmer cannot supersede that record.

Inspection revalidates immutable lineage and the current F-080
read-only status. When evidence expires or F-055 becomes
`MayHaveTransmitted`, a historical record remains visible under its
exact scope but reports `HistoricalOnly` with
`CanDispatch=false`, `CanRetry=false`,
`MigrationComplete=false`. A historical confirmation is never a
transfer capability.

## Tests

Real PostgreSQL 17 integration exercises the full predecessor chain,
independent-actor refusal, exact idempotency, six simultaneous
connections, wrong scope/intent, F-055 demotion and competing lock,
SQL mutation/deletion trigger attacks and JWT superadmin/disabled
HTTP contract with zero provider calls. Separate domain tests
verify canonical hash stability, actor separation and permanent
rejection of execution flags.

F-081 is stacked on F-080. `main` remains unchanged.
